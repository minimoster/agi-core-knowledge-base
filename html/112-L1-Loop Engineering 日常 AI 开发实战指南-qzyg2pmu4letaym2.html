为什么要有Loop Engineering这个名词？
过去几个月 大部分人使用 Coding Agent 的方式其实非常相似：先写一段 Prompt 交给 Agent，等待它完成任务；再检查结果、运行测试，发现问题后补充新的 Prompt，让它继续修改，直到结果满足预期

这个过程本身就是一个Loop，只不过负责观察结果、判断问题并决定“下一步做什么”的循环控制者，一直是坐在屏幕前的人​

如果把这部分工作也交给 AI Agent，让它能够持续执行任务、读取测试和日志、判断目标是否完成，并根据真实反馈自动调整下一步行动，就形成了一个可持续运行的智能闭环​

这正是 Loop Engineering 所关注的问题：它不只是写好一段 Prompt 而是设计一套能够不断“执行—观察—判断—调整—验证”，直至目标达成或触发停止条件的可靠循环

​

一句话结论：Loop Engineering 不是让 AI 无限重试，而是把目标、工具、真实反馈、验证器、重试策略、权限边界与停止条件组合成一个可收敛的工程闭环

1. 核心概念：从 Prompt 到可验证闭环

Loop Engineering 的目标不是“多跑几轮”，而是让每一轮都由真实证据驱动，并且最终能够明确收敛到成功、失败或需要人工介入

普通 Prompt

给出一次指令，模型返回一次结果；人负责检查、追问和重新提示

所以高质量 Loop 的关键不是“让 AI 多试几次”，而是：每一轮必须得到新证据，并根据证据决定下一步

关键原则：“Agent 说已经完成”不是证据；测试退出码、接口响应、性能基线、CI 状态和可审查 Diff 才是证据。

2. 日常开发的标准工作流

日常开发可以按下面七步设计一个最小闭环。小任务可省略状态文件和独立验证者，但不能省略完成条件与验证命令。

  1. 建立基线：先复现问题或运行现有测试，确认当前真实状态。
  2. 定义目标：把“优化一下”“修一下”改成可以判断真假的完成条件。
  3. 限定范围：明确允许修改的目录、接口、依赖和数据。
  4. 指定验证：写出测试、构建、接口请求或 benchmark 命令。
  5. 最小迭代：每轮只解决一个已知问题，修改后立即运行最相关验证。
  6. 失败升级：相同错误重复出现时改变假设；需要扩大范围时请求人工确认。
  7. 最终验收：运行完整回归，审查 Diff，并记录证据与剩余风险。

3. 在 Codex 或者 Claude Code 中如何实际使用

CodeX中内置的两个功能Plan mode 与 Goal

Plan mode：想清楚怎么做

Goal：持续做，直到做完 CodeX中Goal的官方说明 Claude Code中Goal的官方说明

​

复杂任务建议先用 Plan mode 调研影响范围，再用 Goal 固定完成条件，Goal 是闭环中的目标与持续推进机制，但完整 Loop 仍需要你补充验证、权限和停止规则

推荐操作顺序

  1. Plan mode：读取代码、定位入口、梳理影响面，暂不修改
  2. 确认计划：删除无关步骤，补充不能触碰的边界
  3. 设置 Goal：写清完成条件、验证命令和停止条件
  4. 让 Agent 执行：每轮根据真实测试结果做最小调整
  5. 人工验收：检查 Diff、测试是否被削弱、是否存在无关改动

适合 Goal

  • 半小时以上的明确开发任务
  • 需要多轮测试与修复
  • 完成标准可以机械验证

不必使用 Goal

  • 解释一个概念
  • 只读代码定位
  • 修改一句文案
  • 完成条件仍高度模糊

5. 失败重试、权限与停止条件

可以自动继续的场景

  • 读取项目代码
  • 修改任务范围内文件
  • 运行本地测试和静态检查
  • 根据失败日志做最小修复

必须人工确认的场景

  • 生产部署、重启和扩缩容
  • 数据库迁移或数据删除
  • 推送分支、合并 PR、发送外部消息
  • 增加高权限或突破项目边界

停止类型

判断条件

正确动作

成功停止

所有完成条件都有当前证据

汇总证据、Diff 和风险

技术阻塞

缺依赖、环境不可用、权限不足

说明已尝试方案和最小解阻需求

重复失败

连续多轮得到相同错误且无新证据

停止盲目重试，升级给人

范围漂移

修复开始侵入无关模块或公共协议

暂停并重新确认范围

风险门禁

下一步不可逆或影响外部系统

给出操作预览并等待批准

不要设计无限循环：每轮必须产生新证据或改变策略，并设置时间、次数、Token、费用及权限上限

6. 可直接复制的任务模板

需求或者想做什么还不清楚：先用 Plan mode

简单任务：写三部分就够了

简单任务最重要的是：目标 + 验证方式 + 停止条件

复杂任务：使用完整模板

给 Agent 的完成条件越客观，循环越容易收敛。优先使用“命令退出码为 0、失败用例为 0、P95 低于阈值”这类可机械判断的表达

7. 开始前与结束前检查清单

开始前

  • 目标能判断成功或失败，而不是“优化一下”
  • 已有可复现基线，或者计划先补复现用例
  • 明确允许修改与禁止修改的范围​
  • 列出可实际运行的验证命令
  • 设置重复失败、超时和高风险操作的停止条件

执行中

  • 每轮都使用了最新的真实反馈
  • 每轮修改保持足够小，可以定位效果
  • 相同失败出现时改变假设，而不是机械重试
  • 出现范围扩大或权限升级时暂停确认

结束前

  • 完整回归、lint、类型检查或构建已运行
  • 检查测试没有被删除、跳过或削弱
  • 检查 Diff 没有无关修改和敏感信息
  • 最终结论附带命令、结果和剩余风险

最终心法：把 AI 当作能够持续行动的执行系统，而不是只会回答一次的聊天模型；同时把测试、权限和停止条件当作系统边界，而不是事后补充说明
