## 正文

Agent 上下文的质量取决于两件事：**输入前缀能否复用**，以及**模型完成任务所需的事实有没有被保留下来**。盲目增加内容或只保留最新消息，都会损害其中一项。本文围绕五种常见错误展开，帮助你判断上下文为何未命中缓存，并区分缓存问题与模型能力问题。



<a id="78e896cf"></a>
# 先建立一个最小模型：KV Cache 依赖稳定前缀



模型处理一段输入时，会逐个 token 计算注意力层中的 Key 和 Value。已经计算过的部分如果保持不变，后续请求就有机会复用这些结果，不必从第一个 token 重新计算。



可以把一次 Agent 请求简化成下面的结构：



```
[系统提示词]
[工具定义]
[较早的对话历史]
[最近的对话]
[本轮用户消息]
```



缓存复用通常从开头开始匹配。假设前 8,000 个 token 没变，只在末尾追加了 200 个 token，系统便可能复用前 8,000 个 token 的计算结果。如果第 20 个 token 就发生变化，后面即使完全相同，能复用的前缀也只剩很短的一段。



```
请求 A：固定前缀 8,000 token + 新消息 200 token
请求 B：固定前缀 8,000 token + 下一条消息 150 token
                         ↑
                 前 8,000 token 可复用
```



这里说的稳定，不只是意思相同，而是模型最终收到的 **token 序列相同**。字段顺序、消息角色、工具排列和动态文本，都可能改变序列。不同模型服务对缓存的实现和统计口径并不完全一样，但"尽量保持长前缀稳定"是共同的设计原则。

<a id="e5ae3586"></a>
# 错误一：把当前时间写进系统提示词



系统提示词一般位于整个输入的最前面。在这里加入每次都变化的时间戳，会让差异出现在前缀很靠前的位置。



<a id="da6d1f03"></a>
## 错误写法



```json
{
  "role": "system",
  "content": "你是一个日程助手。Current time: 2025-09-14 10:30:45.123456"
}
```



下一次请求可能只过了两秒：



```json
{
  "role": "system",
  "content": "你是一个日程助手。Current time: 2025-09-14 10:30:47.382910"
}
```



时间戳位于系统提示词中，系统提示词之后的工具定义和对话历史也无法继续沿用原来的长前缀。真正改变的只有几十个字符，失去复用机会的却可能是后面的几千个 token。



<a id="cfa6e34d"></a>
## 更合适的做法



**方案 A：把时间追加到对话末尾**



```json
[
  {
    "role": "system",
    "content": "你是一个日程助手。涉及日期计算时，以用户消息提供的当前时间为准。"
  },
  {
    "role": "user",
    "content": "当前时间是 2025-09-14 10:30。提醒我两小时后提交报告。"
  }
]
```



**方案 B：提供 get_current_time 工具按需调用**



```json
{
  "name": "get_current_time",
  "description": "返回当前时区的准确时间",
  "parameters": {
    "type": "object",
    "properties": {}
  }
}
```



这样既能保持公共前缀稳定，也能避免把用不到的动态信息塞进每次请求。

<a id="81274320"></a>
# 错误二：每轮重写用户状态



余额、API 配额、登录状态和任务进度都会变化。把这些字段直接拼进系统提示词或固定用户画像，会产生和动态时间戳相同的问题。



<a id="da6d1f03-1"></a>
## 错误写法



```
SYSTEM:
你是开发者助手。
用户套餐：Pro
本月剩余 API 调用：183
账户余额：¥42.70
```



下一轮只要调用次数从 183 变成 182，前缀就变了。如果这段状态位于工具定义之前，后面的工具说明也要重新计算。



<a id="cfa6e34d-1"></a>
## 更合适的做法



把会变化的状态留在服务端，由一个职责明确的工具读取：



```json
{
  "name": "get_account_status",
  "description": "查询当前套餐、API 剩余调用次数和账户余额",
  "parameters": {
    "type": "object",
    "properties": {}
  }
}
```



如果状态确实会影响每一轮决策，可以把它作为靠近末尾的独立消息追加，而不要改写开头的固定指令：



```json
{
  "role": "user",
  "content": "运行时状态：本月剩余 API 调用 182 次。请继续处理上一轮任务。"
}
```



**判断标准**：模型每一轮都必须知道的状态才进入上下文；只在特定问题中需要的状态，通过工具按需读取。

<a id="ec696db6"></a>
# 错误三：根据使用频率动态调整工具顺序



工具定义常常很长。一个工具可能包含名称、用途、参数类型、必填字段和几百个 token 的说明。十几个工具放在一起，很容易占据数千个 token。



假设某次请求的顺序是：



```
read_file -> write_file -> web_search -> send_email
```



系统根据近期使用频率，把下一次请求调整为：



```
web_search -> read_file -> write_file -> send_email
```



工具本身没有变化，但从第一个工具开始，序列就已经不同。后面的对话历史也失去了原来的前缀位置。



<a id="cfa6e34d-2"></a>
## 更合适的做法



给工具一个固定、可复现的顺序，例如按工具名排序，或维护一份显式注册表：



```python
TOOLS = [
    read_file,
    send_email,
    web_search,
    write_file,
]
```



固定顺序对模型选择正确工具几乎没有影响，却能明显改善性能。如果工具太多，更值得解决的是"本轮需要暴露哪些工具"。比如在代码审查任务中只加载文件读取和代码分析工具，而不是加载邮件、日历和支付工具。筛选后的工具集合仍应保持稳定排序。

<a id="4e2b806a"></a>
# 错误四：用滑动窗口直接删除旧消息



滑动窗口只保留最近若干条消息。假设窗口大小为 10，第 11 条消息进入时，第 1 条消息会被删除。



```
第 10 轮输入：[消息 1][消息 2] ... [消息 10]
第 11 轮输入：        [消息 2] ... [消息 10][消息 11]
```



这会同时造成两个问题：输入的开头从"消息 1"变成了"消息 2"，原来的长前缀不再成立；旧消息中可能包含后续任务仍然依赖的事实或工具结果。



<a id="40f47d6a"></a>
## 一个典型的失败过程



```
第 2 轮：Agent 调用 read_file，得知配置文件中的端口是 8443。
第 3～11 轮：双方讨论鉴权、日志和部署方式。
第 12 轮：用户问"把刚才那个端口同步到部署配置里"。
```



如果 `read_file` 的结果已经滑出窗口，Agent 不再知道"那个端口"是 8443。它可能重新读取文件，也可能根据残留对话猜测。更糟的是，当系统没有明确暴露"信息已丢失"这一事实时，Agent 可能反复执行同一个工具，形成循环。



<a id="cfa6e34d-3"></a>
## 更合适的做法



不要把"控制长度"简单等同于"删除最老消息"。可以把历史分成三类：



- **稳定规则**：目标、约束和用户已经确认的决定

- **任务状态**：已完成步骤、待办项和关键工具结果

- **可丢弃过程**：寒暄、重复解释和不再需要的中间推理




当上下文接近上限时，把前两类压缩成结构化状态，再裁掉可丢弃过程：



```yaml
task_state:
  goal: 更新部署配置并完成验证
  confirmed_facts:
    service_port: 8443
    auth_mode: mTLS
  completed:
    - 已读取应用配置
    - 已确认日志目录
  pending:
    - 修改 deployment.yaml
    - 运行配置检查
```



这段摘要不能只靠模型随意生成后直接覆盖历史。更稳妥的做法是由状态管理层维护字段来源，并保留关键工具结果的引用。需要原文时，可以根据引用重新读取，而不是依赖模型回忆。

<a id="0f75e7c0"></a>
# 错误五：把结构化消息压成纯文本



标准对话接口会明确标记每条消息的角色：



```json
[
  {"role": "system", "content": "你是代码助手。"},
  {"role": "user", "content": "读取 config.yaml。"},
  {"role": "assistant", "tool_call": {"name": "read_file", "arguments": {"path": "config.yaml"}}},
  {"role": "tool", "content": "port: 8443"}
]
```



有些系统会把它改成一段纯文本：



```
SYSTEM: 你是代码助手。
USER: 读取 config.yaml。
ASSISTANT: 调用 read_file("config.yaml")
TOOL: port: 8443
```



纯文本并不必然导致缓存失效。只要序列化方式固定，拼接出的前缀仍然可能命中缓存。问题在于，模型在训练和服务阶段通常接收带有明确角色、工具调用和工具结果边界的标准消息格式。改成自定义纯文本后，模型必须自己推断每段内容属于谁。



这种额外负担会表现为几类错误：



- 忽略已经返回的工具结果，再次调用同一个工具

- 本该发起工具调用时，输出一段看起来像调用指令的普通文本

- 把用户提供的文本误当成系统规则

- 角色边界解析错误，继续了错误一方的话




因此，这一项主要涉及模型能力和协议对齐。只有当纯文本拼接方式本身不稳定（例如每轮都在开头注入动态字段、改变标签或调整片段顺序），缓存才会跟着失效。

<a id="2eaafcf7"></a>
# 把五种错误放在一起看



| **模式** | **缓存为什么受影响** | **对 Agent 能力的影响** | **建议** |
| --- | --- | --- | --- |
| **动态系统提示词** | 开头字段每轮变化 | 通常较小，但成本和延迟上升 | 动态信息放到末尾或按需调用工具 |
| **动态用户配置** | 固定前缀被状态字段改写 | 可能读到过期状态 | 服务端维护，按需查询 |
| **工具动态排序** | 大段工具定义从前部开始变化 | 收益缺少稳定依据 | 固定排序，必要时先筛选工具集合 |
| **滑动窗口** | 删除首部消息，前缀整体左移 | 丢失事实、重复调用、出现循环 | 保存结构化任务状态，按语义裁剪 |
| **纯文本格式化** | 稳定序列化时未必影响缓存 | 角色和工具边界更难解析 | 保留标准 role-content-tool 结构 |

<a id="06ee9920"></a>
# 一个更稳的上下文布局



把稳定内容放前面，把变化内容放后面：



```
1. 固定系统规则
2. 固定版本的工具定义，顺序稳定
3. 长期有效的任务约束和结构化状态
4. 保留下来的关键对话与工具结果
5. 最近几轮消息
6. 本轮动态信息
```



这个布局不要求所有内容永远不变。系统提示词升级、工具版本更新和任务目标调整都是真实需求，发生时就应该修改。需要避免的是没有业务价值的抖动，比如微秒级时间戳、随请求变化的字段顺序，以及为了"可能更好"而调整工具排列。

<a id="45b7e8c2"></a>
# 如何判断问题出在缓存还是模型能力



遇到性能或行为异常时，可以按下面的顺序检查：



1. 保存模型实际收到的完整请求，不要只看业务层的消息对象。

2. 对相邻两轮请求做前缀比较，找到第一个不同的 token 或序列化片段。

3. 查看服务商返回的缓存命中 token 数、输入 token 数和首 token 延迟；没有这些指标时，至少记录请求长度与延迟分布。

4. 保持内容不变，只改消息格式或工具顺序，做单变量对照实验。

5. 缓存命中恢复但 Agent 仍重复调用工具时，继续检查角色边界、工具结果是否保留，以及任务状态是否丢失。




可以用一个简单指标观察前缀稳定性：



```
前缀复用率 = 可复用的前缀 token 数 / 本轮输入 token 总数
```



例如，一轮输入有 10,000 个 token，其中前 8,500 个 token 与上一轮保持一致，那么前缀复用率是 85%。这个比例不等同于服务商账单里的缓存命中率，但适合在应用层定位是哪一次上下文改写破坏了前缀。

<a id="54bbba80"></a>
# 结论



这五种模式可以归到两类问题：



**破坏前缀稳定性**



动态系统提示词、动态状态、工具重排



**损害 Agent 理解能力**



粗暴的滑动窗口、纯文本格式化



更稳的实现并不复杂：固定长前缀，动态信息靠后放；状态由专门机制维护，工具按需暴露并稳定排序；压缩历史时保留事实和结果；模型接口尽量使用它原生支持的结构化格式。这样做既保住缓存，也减少了 Agent 因为"忘记"和"误读"产生的错误。
