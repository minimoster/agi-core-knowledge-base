## 正文

> **为什么要有Loop Engineering这个名词？**
> 过去几个月 大部分人使用 Coding Agent 的方式其实非常相似：先写一段 Prompt 交给 Agent，等待它完成任务；再检查结果、运行测试，发现问题后补充新的 Prompt，让它继续修改，直到结果满足预期
> 
> 
> 
> 这个过程本身就是一个Loop，只不过负责观察结果、判断问题并决定“下一步做什么”的循环控制者，一直是坐在屏幕前的人
> 
> 
> 
> 如果把这部分工作也交给 AI Agent，让它能够持续执行任务、读取测试和日志、判断目标是否完成，并根据真实反馈自动调整下一步行动，就形成了一个可持续运行的智能闭环
> 
> 
> 
> 这正是 Loop Engineering 所关注的问题：它不只是写好一段 Prompt 而是设计一套能够不断“执行—观察—判断—调整—验证”，直至目标达成或触发停止条件的可靠循环





**一句话结论：**Loop Engineering 不是让 AI 无限重试，而是把目标、工具、真实反馈、验证器、重试策略、权限边界与停止条件组合成一个可收敛的工程闭环



<a id="3bb34b80"></a>
# 1. 核心概念：从 Prompt 到可验证闭环



**Loop Engineering 的目标不是“多跑几轮”，而是让每一轮都由真实证据驱动，并且最终能够明确收敛到成功、失败或需要人工介入**



<a id="2af2a218"></a>
### 普通 Prompt



给出一次指令，模型返回一次结果；人负责检查、追问和重新提示



<a id="deabd687"></a>
### Loop Engineering 真正设计的是什么？



提前定义目标、反馈、验证与退出规则，Agent 根据运行结果自行决定下一步



它设计的不是一段 Prompt，而是一个反馈闭环：



![语雀原图](https://cdn.nlark.com/yuque/0/2026/png/27862910/1785749849496-728c1561-15bc-467e-9917-00210787718c.png?x-oss-process=image%2Fwatermark%2Ctype_d3F5LW1pY3JvaGVp%2Csize_59%2Ctext_5rC45rO954mb6YC8IHZ4K3d5emNhYw%3D%3D%2Ccolor_FFFFFF%2Cshadow_50%2Ct_80%2Cg_se%2Cx_10%2Cy_10)



**可以类比为控制系统**



| **组件** | **需要回答的问题** | **例子** |
| --- | --- | --- |
| Goal | 最终什么结果才算完成？ | 测试全部通过且接口兼容 |
| State | 当前进度和已尝试方案是什么？ | 失败测试、已修改文件、下一步 |
| Action | Agent 被允许做什么？ | 读代码、改文件、运行测试 |
| Observation | 从哪里获取真实反馈？ | 测试输出、编译结果、日志、指标 |
| Verifier | 谁来证明结果正确？ | pytest、lint、类型检查、人工审查 |
| Retry | 失败后如何改变策略？ | 基于新证据做最小修复 |
| Stop | 什么时候必须结束？ | 达标、连续同错、缺权限、触及高风险 |



所以高质量 Loop 的关键不是“让 AI 多试几次”，而是：每一轮必须得到新证据，并根据证据决定下一步



**关键原则：**“Agent 说已经完成”不是证据；测试退出码、接口响应、性能基线、CI 状态和可审查 Diff 才是证据。

# 2. 日常开发的标准工作流



*日常开发可以按下面七步设计一个最小闭环。小任务可省略状态文件和独立验证者，但不能省略完成条件与验证命令。*



1. **建立****基线****：**先复现问题或运行现有测试，确认当前真实状态。

2. **定义目标：**把“优化一下”“修一下”改成可以判断真假的完成条件。

3. **限定范围：**明确允许修改的目录、接口、依赖和数据。

4. **指定验证：**写出测试、构建、接口请求或 benchmark 命令。

5. **最小迭代：**每轮只解决一个已知问题，修改后立即运行最相关验证。

6. **失败升级：**相同错误重复出现时改变假设；需要扩大范围时请求人工确认。

7. **最终验收：**运行完整回归，审查 Diff，并记录证据与剩余风险。




| **阶段** | **人负责** | **AI 负责** | **产物** |
| --- | --- | --- | --- |
| 开始前 | 目标、权限、风险边界 | 读取上下文、建立基线 | 计划与基线结果 |
| 执行中 | 处理关键选择和越权请求 | 修改、运行验证、根据反馈纠错 | 小步 Diff 与测试记录 |
| 结束前 | 业务验收、合并和上线决策 | 全量验证、总结证据与风险 | 可审查交付物 |



**推荐：**没有自动化测试时，先让 AI 帮你补充可复现用例或验收脚本，再进入实现循环。否则循环缺少可靠的方向盘

# 3. 在 Codex 或者 Claude Code 中如何实际使用



**CodeX中内置的两个功能Plan mode 与 Goal**



**Plan mode：**想清楚怎么做



**Goal：**持续做，直到做完 [CodeX中Goal的官方说明](https://learn.chatgpt.com/use-cases/follow-goals) [Claude Code中Goal的官方说明](https://code.claude.com/docs/en/goal)



![语雀原图](https://cdn.nlark.com/yuque/0/2026/png/27862910/1785751597951-248a1622-7f9a-4ce7-b160-4b34d257366d.png?x-oss-process=image%2Fwatermark%2Ctype_d3F5LW1pY3JvaGVp%2Csize_48%2Ctext_5rC45rO954mb6YC8IHZ4K3d5emNhYw%3D%3D%2Ccolor_FFFFFF%2Cshadow_50%2Ct_80%2Cg_se%2Cx_10%2Cy_10)





*复杂任务建议先用 Plan mode 调研影响范围，再用 Goal 固定完成条件，Goal 是闭环中的目标与持续推进机制，但完整 Loop 仍需要你补充验证、权限和停止规则*



![语雀原图](https://cdn.nlark.com/yuque/0/2026/png/27862910/1785750352041-77c86368-8be6-4f86-a36d-5c981c76ad66.png?x-oss-process=image%2Fwatermark%2Ctype_d3F5LW1pY3JvaGVp%2Csize_37%2Ctext_5rC45rO954mb6YC8IHZ4K3d5emNhYw%3D%3D%2Ccolor_FFFFFF%2Cshadow_50%2Ct_80%2Cg_se%2Cx_10%2Cy_10)



<a id="79aac742"></a>
## 推荐操作顺序



1. Plan mode：读取代码、定位入口、梳理影响面，暂不修改

2. 确认计划：删除无关步骤，补充不能触碰的边界

3. 设置 Goal：写清完成条件、验证命令和停止条件

4. 让 Agent 执行：每轮根据真实测试结果做最小调整

5. 人工验收：检查 Diff、测试是否被削弱、是否存在无关改动




```
/goal

修复任务偶发停留在 RUNNING 状态的问题。

完成条件：
1. 先增加能够稳定复现问题的测试；
2. 修复后复现测试通过；
3. 成功、失败、取消流程的原有测试全部通过；
4. ruff 与类型检查通过。

范围：只修改任务生命周期模块及对应测试。
禁止：删除或弱化测试、修改公共 API、执行部署。

循环策略：每次根据最新失败做最小修改并重新验证。
停止条件：连续 3 次出现相同失败、需要扩大修改范围、缺少权限或环境不可用。

最终输出：修改摘要、验证命令及结果、剩余风险。
```



<a id="f2e6ce92"></a>
### 适合 Goal



- 半小时以上的明确开发任务

- 需要多轮测试与修复

- 完成标准可以机械验证




<a id="fc4e2531"></a>
### 不必使用 Goal



- 解释一个概念

- 只读代码定位

- 修改一句文案

- 完成条件仍高度模糊

# 4. 四类常见任务的 Loop 设计



| **任务类型** | **核心 Goal** | **主要 Verifier** | **停止信号** |
| --- | --- | --- | --- |
| Bug 修复 | 稳定复现并修复，不破坏相关流程 | 复现测试 + 回归测试 | 无法复现、相同失败反复出现 |
| 新功能 | 正常、异常和边界行为均满足契约 | 单元测试 + 集成测试 + API 契约 | 需求歧义、需要改公共协议 |
| 性能优化 | 指标达到阈值且正确性不下降 | 固定数据集 Benchmark + 基线对比 | 优化无收益、资源成本超限 |
| 线上排障 | 形成有证据的根因和影响范围 | 日志、监控、时间线、只读查询 | 需要生产写操作或重启服务 |



<a id="dcb6fef2"></a>
## Bug 修复最小循环



```
复现问题 → 固化失败测试 → 定位最小根因 → 修改 → 运行相关测试 → 完整回归
```



<a id="50d4c9c0"></a>
## 性能优化最小循环



```
固定环境与数据 → 采集基线 → 定位瓶颈 → 一次只做一项优化 → 重测 → 保留或回退
```



性能任务如果没有优化前基线、固定数据集和重复测量，Agent 无法证明“变快了”；它只能证明代码发生了变化

<a id="1f1b6d49"></a>
# 5. 失败重试、权限与停止条件



<a id="91287656"></a>
### 可以自动继续的场景



- 读取项目代码

- 修改任务范围内文件

- 运行本地测试和静态检查

- 根据失败日志做最小修复




<a id="8946f841"></a>
### 必须人工确认的场景



- 生产部署、重启和扩缩容

- 数据库迁移或数据删除

- 推送分支、合并 PR、发送外部消息

- 增加高权限或突破项目边界




| **停止类型** | **判断条件** | **正确动作** |
| --- | --- | --- |
| 成功停止 | 所有完成条件都有当前证据 | 汇总证据、Diff 和风险 |
| 技术阻塞 | 缺依赖、环境不可用、权限不足 | 说明已尝试方案和最小解阻需求 |
| 重复失败 | 连续多轮得到相同错误且无新证据 | 停止盲目重试，升级给人 |
| 范围漂移 | 修复开始侵入无关模块或公共协议 | 暂停并重新确认范围 |
| 风险门禁 | 下一步不可逆或影响外部系统 | 给出操作预览并等待批准 |



**不要设计无限循环：**每轮必须产生新证据或改变策略，并设置时间、次数、Token、费用及权限上限

<a id="bbe85e48"></a>
# 6. 可直接复制的任务模板



<a id="oqlSd"></a>
### 需求或者想做什么还不清楚：先用 Plan mode



```markdown
请先分析这个需求，读取相关代码，帮我确定：

1. 当前实现和问题基线
2. 合理的修改范围
3. 完成条件
4. 验证命令
5. 风险和停止条件

请最终生成一份可以直接设置为 Goal 的任务描述，
暂时不要修改代码。
```



<a id="db3fd0f7"></a>
### 简单任务：写三部分就够了



```markdown
请通过“修改—验证—根据结果继续调整”的方式完成任务。

【目标】
修复用户查询接口偶发返回 500 的问题。

【验证方式】
运行：
pytest tests/api/test_user.py

【停止条件】
- 测试通过后结束
- 连续三次遇到相同失败且没有新证据时暂停
- 如果需要修改数据库结构，先询问我
```



*简单任务最重要的是：目标 + 验证方式 + 停止条件*



<a id="FuTur"></a>
### 复杂任务：使用完整模板



```markdown
请采用可验证的循环方式完成任务。

【目标】
[最终需要实现什么]

【现状与基线】
[当前行为、失败结果、已有测试或性能数据]

【允许范围】
[可以修改哪些目录、模块和配置]

【禁止事项】
- 不修改无关代码
- 不删除或弱化现有测试
- 不执行部署、推送和数据删除
- 不扩大范围，除非先向我确认

【完成条件】
1. [功能条件]
2. [异常和边界条件]
3. [兼容性条件]
4. 所有指定测试和静态检查通过

【验证命令】
- [单元测试]
- [集成测试]
- [lint 或类型检查]
- [benchmark 或验收命令]

【循环策略】
1. 先建立可复现基线
2. 每轮只处理一个明确问题
3. 每次修改后立即运行最相关验证
4. 根据真实结果决定下一步
5. 最后运行完整回归并检查 Diff

【停止条件】
- 连续三轮出现相同失败且没有新证据
- 需要扩大修改范围或改变公共契约
- 缺少权限、依赖或必要信息
- 下一步属于部署、删除等高风险操作

【最终输出】
- 修改内容
- 验证命令及结果
- 剩余风险
```



给 Agent 的完成条件越客观，循环越容易收敛。优先使用“命令退出码为 0、失败用例为 0、P95 低于阈值”这类可机械判断的表达

<a id="7c44cc34"></a>
# 7. 开始前与结束前检查清单



<a id="592ca286"></a>
## 开始前



- 目标能判断成功或失败，而不是“优化一下”

- 已有可复现基线，或者计划先补复现用例

- 明确允许修改与禁止修改的范围

- 列出可实际运行的验证命令

- 设置重复失败、超时和高风险操作的停止条件




<a id="46e38679"></a>
## 执行中



- 每轮都使用了最新的真实反馈

- 每轮修改保持足够小，可以定位效果

- 相同失败出现时改变假设，而不是机械重试

- 出现范围扩大或权限升级时暂停确认




<a id="f78626bb"></a>
## 结束前



- 完整回归、lint、类型检查或构建已运行

- 检查测试没有被删除、跳过或削弱

- 检查 Diff 没有无关修改和敏感信息

- 最终结论附带命令、结果和剩余风险




**最终心法：**把 AI 当作能够持续行动的执行系统，而不是只会回答一次的聊天模型；同时把测试、权限和停止条件当作系统边界，而不是事后补充说明

总结：loop其实我感觉就是一种范式 一种思想 看具体在什么层面的应用
